Insight 1

Front-loaded comprehension tax

The harness is a one-time read of stack, patterns, and gates before any code. For a single well-scoped task that is overhead. For repeated work on the same repo it amortizes. Run A’s first write was PROGRESS.md — process before product. Run B’s first write was the API client.

Tool calls: volume converges, distribution does not

106 vs 116 total calls, 51 vs 48 reads — discovery load is almost identical. Run A spends more on Write. Run B spends more on Shell (live environment debugging). Tool-call count is a weak proxy for “how much work.”

Insights

Insight 2

Run B was not “no guardrails”

User rules (Conventional Commits, TS strict, Jest) and skills (react-native-patterns, commit-after-change, tdd) still applied. That is why Run B still wrote loading/error states, tests, and a commit. The repo harness’s distinctive additions were narrower: compound components, PROGRESS.md, test-per-function, and a pre-tested verify.sh gate.

Insight 3

Verification gates store known-working config

Losing verify.sh forced rediscovery of jest-expo + pnpm + msw/node export conditions. Gates are not only correctness checks; they are institutional memory about which version of which tool needs which tweak.

Insight 4

Spell architectural choices explicitly

The model has weak defaults for design patterns and follows the most idiomatic path without explicit guidance. Compound components did not emerge from a “patterns” skill alone. If the team wants them, the harness must say so.

Insight 5

Fingerprint of effort ≠ call count

Similar totals, different jobs: Run A writes files and updates progress; Run B shells through a broken test runner. A harness with a working gate shifts the mix from environment debugging to feature implementation.

Insight 6

Scope creep was not tested

Neither run paginated or entered Step 2. The prompt (“Step 1 only”) was tight enough that vertical-slice guidance and PROGRESS.md were not the thing that prevented drift. A fuzzier, larger task would be needed to measure that guardrail.

Bottom line

With harness

Slower front-end (discovery), clean verification path, test-per-function (~23 vs 9), a PROGRESS.md trail, and an explicit compound-component structure.

Without repo harness

Faster start, then live Jest/MSW/jest-expo debugging; fewer, coarser tests; no formal work trail; architecture defaulted to hooks. Not reckless — user-level rules did real guardrail work.

For a single task in isolation, the harness imposes overhead. For repeated tasks or team consistency, that overhead is an investment. The real value is not “better code” but reducing rediscovery and amplifying test organization, plus encoding known-working toolchain config.

Caveats. No token or cost data — do not compare compute from these files. Thinking traces were not persisted (thinking_chars = 0). Wall clock is file birth/mtime plus prompt timestamps, not model inference time. Metrics-page authoring is excluded from implementation duration. This is not a perfectly clean “no AI” ablation: user-level Cursor skills and rules still applied in Run B. Single task, N = 1; patterns may not generalize.
